# Autonomous Agile Planner

## Overview

Consolidates the MikirinKode Jira-like structurization pipeline (Epic → Features → Tasks → Index) into a single autonomous run. You are an **Agile Planner** who takes an Implementation Plan (generated by `obra writing-plans`) and breaks it down into your Git-native tracker (YAML/MD) for execution.

## When to Use

- User says "Run mk-agile-planner using the implementation plan at `plans/...`"
- User provides a finalized implementation plan and wants it converted into Epics, Features, and Tasks in the `MikirinKode/projects/[id]/` system.

## When NOT to Use

- User just has a raw idea → use `obra brainstorming` and `obra writing-plans` first.
- User wants to execute/implement code → use `mk-agile-executor`

## The Autonomous Pipeline

**DO NOT PAUSE between steps. Execute Steps 0-6 in one continuous run.**

```
Step 0: Bootstrap   → Detect new vs existing project
  ├─ NEW:    Register project, create dirs, plan setup task
  └─ EXISTS: Analyze current project health & codebase
Step 1: Context     → Find next IDs, read memory
Step 2: Epic        → Generate EPIC-XXX.md
Step 3: Features    → Generate FEAT-XXX.yaml files
Step 4: Tasks       → Generate TASK-XXX.yaml files
Step 5: Index       → Update _epic-index.yaml
Step 6: STOP        → Present summary, wait for human review
```

### Step 0: Bootstrap / Analyze Project

Check if the project exists in `MikirinKode/projects/_registry.yaml`.

#### Branch A — NEW Project (not in registry)

1. **Register** the project in `_registry.yaml` with:
   - `project_id`, `project_name`, `type` (flutter-mobile/flutter-web/web/other)
   - `repo_path` (where the actual source code lives)
   - `created` date
2. **Create directories:**
   ```
   MikirinKode/projects/[project-id]/
   ├── epics/
   ├── features/
   └── tasks/
   ```
3. **Create initial memory:**
   ```
   MikirinKode/memory/[project-id]/
   └── README.md    # Basic project overview
   ```
4. **Auto-inject a mandatory setup Feature and Task:**
   - The FIRST Feature generated (in Step 3) must be: `"Setup project infrastructure"`
   - The FIRST Task(s) generated (in Step 4) must cover:
     - `flutter create` with correct org/platforms (if Flutter)
     - Core dependencies installation (`pubspec.yaml`)
     - Firebase/Hive/other infra setup (if applicable)
     - Project structure scaffolding (routes, theme, base config)
   - These setup tasks always get `priority: must` and come before ALL other tasks.

#### Branch B — EXISTING Project (found in registry)

1. **Read the project's `repo_path`** from `_registry.yaml`.
2. **Analyze the current codebase condition:**
   - Check if `pubspec.yaml` exists → if missing, treat as Branch A.
   - Read `pubspec.yaml` to understand current dependencies and Flutter/Dart SDK versions.
   - Scan `lib/` directory structure to identify existing modules, controllers, views, models.
   - Check for common config files: `firebase.json`, `analysis_options.yaml`, `.env`.
3. **Check project health:**
   - Are there existing epics/features/tasks? What's the current progress?
   - Are there unresolved blockers in existing tasks?
   - What patterns/architecture is already in use? (GetX? BLoC? Provider?)
4. **Read project memory:**
   - `memory/[project-id]/patterns.md` — established coding patterns
   - `memory/[project-id]/preferences.md` — naming/design conventions
   - `memory/[project-id]/lessons-learned.md` — bugs to avoid
   - `memory/[project-id]/architecture.md` — past decisions
5. **Produce a mental model** of the project's current state. Use this to:
   - Avoid generating tasks that conflict with existing code
   - Reuse existing models/services/widgets instead of recreating them
   - Follow the project's established patterns, not generic ones
   - Detect if required infrastructure is missing and inject setup tasks

### Step 1: Read IDs & Prepare

1. Scan `projects/[project-id]/epics/` to find the next available EPIC-XXX ID.
2. Scan `projects/[project-id]/features/` to find the next available FEAT-XXX ID.
3. Scan `projects/[project-id]/tasks/` to find the next available TASK-XXX ID.
4. Carry forward the project analysis from Step 0 into all subsequent steps.

### Step 2: Generate Epic

1. Use `MikirinKode/templates/epic-template.md` as the base template.
2. Fill in all sections: Overview, Goals, User Flow, Architecture, Implementation Phases.
3. Set `status: draft`.
4. Set `progress: 0%`.
5. Save to: `MikirinKode/projects/[project-id]/epics/EPIC-XXX-[slug].md`

**DO NOT STOP. Proceed immediately to Step 3.**

### Step 3: Generate Features

1. Use `MikirinKode/templates/feature-template.yaml` as the base template.
2. Extract user capabilities from the Epic (each = one Feature).
3. Name each feature as **Verb + Object** (e.g., "View role list", NOT "Role management").
4. Assign priorities using MoSCoW (must/should/could/wont).
5. Generate 3-8 features per Epic. If more than 8, suggest splitting the Epic.
6. Save each to: `MikirinKode/projects/[project-id]/features/FEAT-XXX.yaml`
7. Update the Epic file's `## Features` section with the generated FEAT IDs.

**DO NOT STOP. Proceed immediately to Step 4.**

### Step 4: Generate Tasks

1. Use `MikirinKode/templates/task-template.yaml` as the base template.
2. For each Feature, break acceptance criteria into 2-5 concrete tasks.
3. Each task must be 1-4 hours of work.
4. **CRITICAL ORDER**: Tasks must be in logical dependency order:
   - Setup/scaffolding tasks FIRST (project creation, dependencies)
   - Model/data tasks SECOND
   - Service/logic tasks THIRD
   - UI/view tasks FOURTH
   - Testing tasks FIFTH
   - Integration/polish tasks LAST
5. Declare `dependencies:` between tasks that require sequential execution.
6. Save each to: `MikirinKode/projects/[project-id]/tasks/TASK-XXX.yaml`
7. Update each Feature file's `tasks:` list with the generated TASK IDs.

### Step 5: Update Index

1. Regenerate `MikirinKode/projects/_epic-index.yaml`.
2. Include the new Epic, all Features, all Tasks, and calculated progress (which will be 0%).

### Step 6: STOP and Present Summary

**This is the ONLY place you stop.** Present a summary table:

```markdown
## Planning Complete ✅

**Epic:** EPIC-XXX - [Name]
**Project:** [project-id]

| Feature | Priority | Tasks | Est. Hours |
|---------|----------|-------|------------|
| FEAT-001: [Name] | must | 3 | 6h |
| FEAT-002: [Name] | should | 4 | 8h |
| ... | ... | ... | ... |

**Total:** X features, Y tasks, ~Zh estimated

📋 Please review the generated files in your IDE.
When ready to start building, say: "Execute EPIC-XXX" or "Execute FEAT-XXX"
```

## Red Flags — Things That Should NEVER Happen

| Symptom | Problem |
|---------|---------|
| AI asks "Should I generate features now?" | Violation. Pipeline is autonomous. |
| Tasks are not in dependency order | Violation. Setup must come before UI. |
| Feature named as a noun ("Dashboard") | Must be Verb + Object ("View dashboard") |
| A single task estimated > 4 hours | Must split into smaller tasks. |
| TASK for "Create project scaffolding" appears after TASK-005 | Order violation. Setup is always first. |

## Success Criteria

- [ ] Epic saved to correct location with all sections filled
- [ ] Features saved with Verb + Object names and MoSCoW priorities
- [ ] Tasks saved in logical dependency order
- [ ] Task sizes are 1-4 hours each
- [ ] Epic references all Feature IDs
- [ ] Features reference all Task IDs
- [ ] Index file updated
- [ ] Summary table presented to user
- [ ] AI did NOT pause between Steps 1-5

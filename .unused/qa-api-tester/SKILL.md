# QA API Tester

Execute API test cases from a QA spreadsheet (.xlsx) against a live environment and update the spreadsheet with pass/fail results.

## Overview

This skill reads a QA test case spreadsheet (generated by `qa-test-generator` or manually), identifies API-testable cases, executes HTTP requests, compares actual responses to expected results, and writes Pass/Fail status back to the xlsx.

## Prerequisites

- **Network must be enabled** — this skill makes HTTP requests to external APIs
- **Input xlsx** must follow the qa-test-generator schema (columns A-L)
- **User must provide**: base URL and authentication method

## Workflow

```
User provides: xlsx file + base URL + auth info
        ↓
1. Read xlsx → filter rows where Category = "API" or Test Data contains METHOD:
        ↓
2. Authenticate → obtain bearer token (if login-based auth)
        ↓
3. For each API test case:
   a. Parse Test Data column → extract METHOD, ENDPOINT, HEADERS, BODY, EXPECT_STATUS, EXPECT_BODY
   b. Execute HTTP request
   c. Compare actual vs expected
   d. Write Status (Pass/Fail), Actual Result, Timestamp to xlsx
        ↓
4. Recalculate Summary sheet formulas
        ↓
5. Present updated xlsx to user
```

## How to Collect Input from User

Before running tests, ask the user for:

1. **Base URL** — e.g., `https://caritahub-indo-ssi-dev.int.weeswares.com`
2. **Auth method** — one of:
   - `bearer` — user provides a token directly
   - `login` — user provides email + password + login endpoint; skill calls it first to obtain token
   - `none` — no authentication needed
3. **Which test cases to run** — options:
   - `all` — run all API-parseable test cases
   - `category:API` — only rows with Category = "API"
   - `priority:P1` — only P1 test cases
   - `range:TC-001:TC-010` — specific range

## Test Data Column Format (API Tests)

For this skill to auto-execute a test case, the **Test Data** column (column H) must contain structured key-value pairs. Each key on its own line:

```
METHOD: GET
ENDPOINT: /api/v1/members/sick
HEADERS: {"Content-Type": "application/json"}
BODY: {"start_date": "2025-01-01", "end_date": "2025-01-31"}
EXPECT_STATUS: 200
EXPECT_BODY_CONTAINS: ["member_id", "name"]
EXPECT_BODY_MATCH: {"success": true}
```

### Field Reference

| Key | Required | Description | Example |
|-----|----------|-------------|---------|
| METHOD | Yes | HTTP method | GET, POST, PUT, PATCH, DELETE |
| ENDPOINT | Yes | Path appended to base URL | /api/v1/members |
| HEADERS | No | JSON object of extra headers (auth added automatically) | {"X-Custom": "value"} |
| BODY | No | JSON request body (for POST/PUT/PATCH) | {"name": "John"} |
| EXPECT_STATUS | Yes | Expected HTTP status code | 200, 201, 400, 401, 404 |
| EXPECT_BODY_CONTAINS | No | List of keys that must exist in response body | ["id", "name", "status"] |
| EXPECT_BODY_MATCH | No | JSON object — each key:value must match in response | {"success": true} |
| EXPECT_BODY_NOT_CONTAINS | No | Keys that must NOT exist in response | ["password", "secret"] |
| EXPECT_ERROR_MESSAGE | No | Substring that must appear in error response | "Invalid credentials" |

### Variable Substitution

The following variables are auto-replaced at runtime:

- `{{base_url}}` — the base URL provided by user
- `{{token}}` — the bearer token (from direct input or login flow)
- `{{timestamp}}` — current ISO timestamp
- `{{tc_XXX_response.field}}` — reference a field from a previous test case response (for chained tests)

Example:
```
METHOD: GET
ENDPOINT: /api/v1/members/{{tc_001_response.member_id}}
EXPECT_STATUS: 200
```

## Execution Logic

### Authentication

```python
# If auth method is "login":
login_response = requests.post(
    f"{base_url}/{login_endpoint}",
    json={"email": email, "password": password}
)
token = login_response.json().get("access_token") or login_response.json().get("token")
```

The token is then injected as `Authorization: Bearer {token}` on all subsequent requests.

### Test Execution per Row

```python
for each test_case:
    1. Parse Test Data → extract METHOD, ENDPOINT, BODY, HEADERS, EXPECT_*
    2. Build full URL: base_url + ENDPOINT
    3. Inject auth header
    4. Execute: requests.request(method, url, json=body, headers=headers, timeout=30)
    5. Compare:
       - status_code == EXPECT_STATUS → pass/fail
       - EXPECT_BODY_CONTAINS keys exist in response → pass/fail
       - EXPECT_BODY_MATCH values match → pass/fail
       - EXPECT_BODY_NOT_CONTAINS keys absent → pass/fail
       - EXPECT_ERROR_MESSAGE substring found → pass/fail
    6. ALL checks must pass → "Pass", ANY fails → "Fail"
    7. Store response for variable substitution in later tests
```

### Result Writing

For each executed test case, update the xlsx row:

| Column | Update |
|--------|--------|
| J (Status) | "Pass" or "Fail" |
| K (Tested By) | "Claude AI (automated)" |
| L (Notes) | Append actual result summary: status code, response snippet (max 200 chars), timestamp, failure reason if failed |

### Styling for Results

- **Pass**: Green background on Status cell (RGB: 198, 239, 206)
- **Fail**: Red background on Status cell (RGB: 255, 199, 206)
- **Skipped** (non-parseable): Yellow background (RGB: 255, 249, 196), Notes = "Skipped: not API-parseable"

## Handling Non-API Test Cases

Test cases without structured Test Data (manual/UI tests) are **skipped**, not failed:
- Status → leave blank (or "Skipped" if user chose `all`)
- Notes → "Manual test — requires human execution"

## Error Handling

| Scenario | Behavior |
|----------|----------|
| Network unreachable | Stop execution, report error, save partial results |
| Auth fails (login returns non-200) | Stop execution, report auth error, don't run any tests |
| Single test timeout (>30s) | Mark as "Fail", Notes = "Timeout after 30s" |
| Invalid Test Data format | Mark as "Skipped", Notes = "Parse error: [detail]" |
| SSL certificate error | Report to user, offer to retry with verify=False |
| Response is not JSON | Compare only status code, note "Response is not JSON" |

## Output

1. Update the xlsx in-place (preserve all formatting from qa-test-generator)
2. Recalculate Summary sheet: `python /mnt/skills/public/xlsx/scripts/recalc.py`
3. Add a new sheet **"Test Run Log"** with:
   - Run timestamp
   - Base URL (masked after first 30 chars for security)
   - Auth method used
   - Total executed / passed / failed / skipped
   - Execution duration
4. Present the updated xlsx to user

## Integration with qa-test-generator

When `qa-test-generator` creates test cases for API-platform tasks:
- Test cases with Category "API" should have structured Test Data following this skill's format
- The `qa-test-generator` skill should read `references/test-data-format.md` from this skill directory to ensure compatible output

**Pipeline:** Task Brief JSON → `qa-test-generator` (xlsx) → `qa-api-tester` (executed xlsx with results)

## Common Mistakes

| Mistake | Fix |
|---------|-----|
| Running without checking network | Always verify network first: `requests.get(base_url, timeout=5)` |
| Hardcoding token in xlsx | Use {{token}} variable, inject at runtime |
| Failing all tests on auth error | Stop immediately, report auth issue, save partial xlsx |
| Overwriting user's manual test results | Only update rows that were auto-executed |
| Not preserving xlsx formatting | Use `load_workbook()` without `data_only=True` to keep formulas |
| Printing full response bodies | Truncate to 200 chars in Notes column |
